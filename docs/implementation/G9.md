# G9 — Playbook start, cancel and activation

Task `steady-cascade-45.10`, implemented November 4, 2026. The Playbooks page now has three controls: **Start run** on the Recent runs pane, **Cancel run** in the run inspector header, and **Activate definition** and **Roll back activation** in a new "Activation for new runs" panel on the activation detail.

Every control sends a frozen `dashboard-actions-1` intent to `POST /api/v1/actions`. After that, it looks up `GET /api/v1/operations/{id}` once immediately and then every 2000 ms. The frozen bytes are reused for every lookup and for every "Retry exact submission".

**Live status: the four `playbook.*` action kinds are not offered on aq-server main.** D9 (`crisp-meadow-36.10`, migration `0085_playbook_activations`) ships direct owner routes, outside the action union. Live, every G9 control therefore renders disabled with the session's reason, "Not offered by this AQ server". This is the honest unavailable state the operator asked for, and the cross-repo follow-up below asks D9 for the union kinds. **Full-page acceptance against 06, and G11 visual/WCAG sign-off, remain open.**

## Delivered behavior

- **Shared action control.** `src/features/playbooks/PlaybookAction.tsx` holds the trigger, the modal dialog and the operation state machine.
  - **Gating.** `dashboard.actions` is checked first, then the per-kind capability (`playbookActions.ts`). A disabled control shows its reason both as visible text and as the button title. Access lost (401/403) takes precedence, then the capability reason, then a domain block such as a finished run.
  - **Outcomes:**
    - pending shows each control's "requested — awaiting confirmation" copy;
    - confirmed shows the confirmed copy;
    - conflict (409) shows "Conflict — your draft is preserved." plus the server's current versions;
    - rejected (400/404/413/422) shows the server's message;
    - 410 shows the retired-receipt copy;
    - 426 is reported as incompatible;
    - transport errors and 5xx are reported as unknown.
  - **Preserved inputs.** Inputs are locked, not cleared, once submitted. Conflict and rejection offer "Reload current versions", which refreshes the subject and keeps the draft. An unsettled operation keeps its dialog and labels the trigger "· operation", so reopening shows the same operation, not a new one.
  - **Draft identity.** The draft is keyed by principal, authorization revision, project and subject, so a change of access or subject never carries a draft over. Start passes a stable `instance` so that changing the binding keeps the open dialog.
- **Cancel (`RunActions.tsx`).** Cancel is an intent.
  - The user must confirm it: "Confirm cancellation request. This does not prove the run stopped." A Reason field is optional.
  - Pending reads "Cancellation requested — awaiting confirmation."; confirmed reads "Cancellation requested".
  - Neither outcome relabels the run. The badge stays the server's state until a refreshed read changes it.
  - Finished runs, and runs already cancelling, are blocked with their reason.
- **Start (`StartRun.tsx`).** The user chooses a binding from the current activations catalog, and an entry from the bound definition's entries. If that definition is not on the first catalog page, the user types the entry name, and the page says why.
  - Inputs are typed rows (name; Text, Number or True/false; value), with a maximum of 32 rows and no raw JSON editor.
  - `parseInputs` rejects duplicate, blank and non-numeric rows before freezing.
  - The subject is the `playbook_binding` at its revision.
- **Activate and roll back (`ActivationActions.tsx`, mounted at `CurrentCatalog.tsx:100`).** The panel states which definition is active for new runs and at which binding revision. It also says: "Activation affects future runs only. Existing runs keep their pinned definition. Installing and compiling are separate operations."
  - Both actions require confirmation, and both pin the expected binding revision.
  - Activate offers only installed definitions other than the current one. With none available it is blocked: "No other definition is represented in this namespace".
  - Install and compile are not offered here.
- **No resume control.** Resume cannot bypass a decision, and answering decisions is F5, so G9 adds no resume control.
- **Mock mode.** `src/mocks/playbooks.ts` adds the four PROPOSED action capabilities to the labelled fixture bootstrap. `playbookActionHandlers()` (`playbooks.ts:186`) answers `playbook.*` kinds only: admission is pending and the first lookup confirms with a fixture receipt. Other kinds fall through to the next handler. The fixture catalog has a single definition, so Activate shows its blocked reason in mock mode.

Shared files touched:
- `src/features/actions/actionClient.ts`: type-only. `FrozenAction.kind` is widened to `string` so feature kinds use the same transport.
- `src/mocks/handlers.ts`: one line, to compose the playbook action handlers in fixture mode.

There are no shell, route or capability-registry changes.

Remaining differences and limits:

- **"Definition v3 is active for new runs" on the run pin strip (06) is not shown.** The run read does not carry its binding or activation revision, so the run side cannot honestly name the current activation. The activation detail states it instead. This is part of the follow-up.
- **"Create playbook"** (06, top right) is out of scope (authoring).
- **Conflict review.** It keeps the chosen definition only while the catalog stamp is unchanged. If the server's metadata revision changes, the detail query key changes and the activation detail remounts with a fresh draft.
- **Live controls are disabled** until aq-server offers the union kinds below.
