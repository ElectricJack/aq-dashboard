# F5 — agent questions in the decision inbox (dashboard side)

The server side is aq-server PR #87 (`docs/implementation/F5.md` there). In that PR an agent asks with `POST /v1/agent/questions`, the server records a typed `question` decision at revision `"1"`, and the owner answers through the dashboard-actions-1 kind `question.answer`.

## What the dashboard does

- **Inbox.** Pending questions are listed in the decision inbox, above the reviews, under an "Agent questions" list. Each row shows the task title, the project, the question text (clamped to two lines) and the expiry. Answered questions appear under Resolved. The Open/Resolved count and the subtitle include them. Refresh reloads both lists.
- **Question page.** The link is `/decisions/{decision_id}?kind=question`. It reuses the server's allowlisted `/decisions/{decisionId}` SPA route, so it works as a direct, signed-in link from a notification. The middle column shows the exact question, the task, the expiry and any recorded answer with its delivery (woke the waiting agent, or queued as task mail). The right column shows the context: project, task, asked, expires or answered, and the decision ID with its revision. On phones the page follows the review page's list-then-detail layout, with a way back.
- **Answer.** The answer form sits inside the question column. It is not sticky, so it cannot cover the question or keyboard focus. It submits `question.answer` with `subject {type: "decision", id, revision}`, `expected_versions {decision: revision}` and the strict payload `{operation_id, expected_revision, answer}` (at most 16,000 bytes). The bytes are frozen once. Possible outcomes:
  - **Confirmed:** the question detail is refetched and the question-inbox queries are invalidated, so the question moves to Resolved.
  - **Conflict or rejection** (409 `stale_revision`/`id_conflict`, 400/404/422): the draft is kept. The answer can only be sent again after a deliberate "Refresh question", and the new attempt is a new operation.
  - **Unknown or pending** (transport error, 5xx, 202): the form offers "Check status" (operation lookup) and "Retry same answer" (identical bytes).
  - **426:** answering is disabled with an upgrade notice.
- `adaptActionOperation` accepts an optional `FrozenAction.project`. The scope check needs it because the `question.answer` payload has no `project_id`.

## Server gap (blocking live use)

aq-server main records question decisions but serves **no human read** of them. The review inbox (`/api/reviews/decisions`) reads only `human_decision_requests`. Bootstrap advertises neither a question read nor a question answer capability. The dashboard is therefore built against a proposed read, and it stays inert on a live server until that read exists:

- the read is the live `question-inbox-1` schema in `contracts/live/dashboard-read-g2/schema.json` (fixtures alongside, vendored from aq-server PR #89): `GET /api/questions/decisions?state=open|closed&limit&project_id&cursor` and `GET /api/questions/decisions/{id}`, both `question-inbox-1`;
- the capabilities are `questions.read` (both routes) and `questions.answer` (the action; it also needs `dashboard.actions`).

When `questions.read` is absent, no question request is made and the inbox is unchanged. Neither capability is listed in `bundle-requirements.json`, so current servers stay compatible. The vendored `contracts/live/dashboard-actions` (with the `dashboard-read` schema its checker needs) was refreshed from aq-server `4b9d732b`, so it includes `question.answer`.
