Dashboard product and interaction design

Status: implementation specification proposed from the accepted visual direction. Date: 2026-10-31. The user approved the mockup direction; this document supplies implementation decisions, not a claim that the APIs or application are implemented.

Read with the architecture baseline, API contract proposal, implementation plan, and contract audit. Where a PNG conflicts with this text, this text governs behavior. The focused Agents design supersedes the earlier tiled-terminal default.

1. Product outcome and boundaries

An operator should immediately understand what needs attention, what is running, what it produced, and how to intervene. Reading a result and requesting a correction should be possible on a phone. Desktop provides space for investigation and terminal work; mobile provides a deliberate single-pane composition.

AQ remains the authority for authentication, scope, scheduling, actions, lifecycle, evidence retention and decisions. The browser owns presentation, navigation, drafts and disposable caches. It connects only to AQ's human API. Component databases, worker endpoints, provider credentials and internal graph services are never browser dependencies.

The complete target includes Overview, Supervisor, Work, Results, Decisions, Agents, Playbooks, Knowledge and basic Settings. Implementation can ship coherent capability-gated slices; the first inspection release does not constitute delivery of the full design. Bulk administration, arbitrary workflow editors, offline committed edits and a separate dashboard server are outside this release.

3. Application shell and information hierarchy

Navigation order is Overview, Supervisor, Work, Results, Decisions, Agents, Playbooks, Knowledge, with Settings and identity at the bottom. Supervisor is directly below Overview. The desktop rail stays visible in full-page chat. Explicit terminal Expand may collapse it.

The persistent top area contains scope, provider quota, search and connection/freshness affordances. The quota strip remains above every destination, including full chat and terminal focus. Quota is account-scoped and labelled accordingly; selecting a project must not imply that an account-wide percentage became project usage.

Each provider entry shows provider/account label, percent used, actual window name, reset time and observation freshness. Never invert remaining percentage into used without a defined source field. Unknown is “Usage unavailable,” never zero. A stale value retains its timestamp and stale label. Multiple windows disclose their individual percentages and reset times; do not invent a combined percentage. The preferred window comes from server policy, not a hard-coded assumption that “primary” means weekly. Distinguish quota, provider availability, session token/cost accounting and worker capacity.

All projects means all projects the current principal may see, with server-derived aggregate counts. Changing scope updates applicable queries and URL state. Global supervisor identity does not change. Counts must state when partial, filtered or estimated. Search returns bounded, scoped results grouped by task, session, result, playbook and knowledge; keyboard and touch share the same search dialog.

Routes:

A deep link to inaccessible content returns a neutral unavailable view, without leaking its title. Docked supervisor is shell state; expansion navigates to /supervisor and remembers the return location.

4. Overview, Work and Decisions

Overview. Lead with Needs attention: pending human decisions, blocked or failed work requiring intervention, and uncertain operations requiring reconciliation. Each row shows reason, impact, age, exact subject and next permitted action. Follow with active work and recent results. Capacity and operational health are secondary. Empty attention means “Nothing needs your attention” only after a successful complete query; loading or failed reads must not resemble an empty queue.

Work. List and graph use the same scope/filter/selection. Rows show title, project, lifecycle, execution observation, blocker/wait reason, relevant agent and latest result. Detail contains requirements, acceptance criteria, dependency explanation, attempts, evidence, source/delivery state and history. Server explanations determine readiness; the browser must not derive runnable status from a graph traversal.

The graph initially renders a bounded neighborhood around the selected task, with a 100-node target cap and explicit omitted counts/expansion controls. Hierarchy, execution dependencies and informational evidence links have distinct styling and labels. Stable positions preserve orientation when data changes. A textual dependency list offers the same navigation without graph interaction. Mobile opens a dedicated graph view deliberately; task lists remain the default.

Decisions. One inbox can discover reviews, questions and failure interventions, but each retains its domain-specific form and permission. Show exact source/task/result revision, requested judgment, evidence availability, previous responses and downstream effect. Approve/reject/answer binds that revision. A newer subject shows a superseded warning; no automatic retargeting. The mobile action bar must not hide evidence or keyboard focus. Submission remains pending until the server confirms; a conflict retains the draft and presents a deliberate refresh/review path.

Cancellation is an intent, not proof the process stopped. Source retained, result submitted, result accepted, task complete, candidate published and change merged/deployed are distinct facts wherever shown.

5. Supervisor: docked and full-page conversation

The docked panel and full-page view share one conversation state, message collection, attachments, draft and reading position. Full page fills the area beside the rail and below the provider strip; message text has a comfortable maximum reading width. The phone always uses a full-page conversation. No duplicate conversation or new supervisor session is created by changing presentation.

The header explicitly says Global supervisor. Project scope can attach context but never silently changes recipient. A context chip identifies the exact task/result/document revision and can be removed before send. Result cards link to retained evidence. Message history is paginated; auto-scroll only when the reader is already at the bottom. Otherwise show a new-message marker.

The composer supports plain text and authorized artifact/context references. Enter sends on desktop; Shift+Enter adds a newline; mobile provides a labelled Send button. IME composition must not send prematurely. A local pending message remains identifiable through send retries. Show admitted/queued, delivery evidence, unknown and failure separately; an acknowledgement is not proof that the requested work was performed.

The supervisor can propose a feedback task. Display its editable draft and the explicit Create action unless an existing configured workflow already authorizes creation. An ordinary chat message must not imply blanket approval of later actions. If central supervisor authority is unavailable, show a clear unavailable state and preserve the draft; do not route messages to an arbitrary worker.

6. Agents and terminal workspace

The roster shows current sessions with task, project, chosen provider/model/harness, observed state/freshness, wait reason and controller presence. Session detail distinguishes profile/configuration revisions, effective permissions, actual execution authority and last observed process activity. Secrets and unscoped prompts are excluded.

Opening a session uses one large terminal by default. Compact session tabs/switcher replace a permanent roster. Details, transcript and durable Message are on-demand drawers. Split is explicit, at most two visible panes initially, available only when each pane fits at least 80 columns at the selected readable font size. Never shrink font to force a split. On smaller widths offer tabs; preserve selected session and local view state through layout changes.

Watch is read-only. Taking control requires a distinct action and confirmed exclusive server lease/fence; display controller identity, lease state and expiry. Other viewers do not resize the shared tmux pane. Only confirmed control enables keystrokes, paste and resize. On mobile, use internal horizontal terminal panning and a minimum 14px monospace default; provide text-size controls. The plain-text transcript is an alternative reading mode with provenance/gaps, not a fake editable terminal.

Connection loss freezes input and labels the last observation. Reconnect requests authorized replay/snapshot for the same identity and epoch; it never relaunches a process or acquires control automatically. Unknown input delivery blocks later input until the specified fresh-capture resolution. Do not replay buffered keystrokes after reconnect. Follow the exact negotiated finite/epoch input mode and published limits; ordinary mutation retries are not a terminal-input recovery algorithm.

On phones, Back returns to the roster. Hide normal bottom navigation in focused terminal mode. Use visible viewport height and safe-area insets when the keyboard opens; keep quota, terminal status and essential input controls visible while collapsing secondary chrome. Offer Esc, Tab, Ctrl and arrows with clear active modifier state. Rotation must not acquire control or restart; a controller resize is debounced and sequenced, never sent from a viewer. Test real IME, paste, selection, alternate-screen programs and wide Unicode.

Disable unsafe terminal escape actions, automatic clipboard access and untrusted links. Bound scrollback, frame queues and renderer work. Durable Message and domain Cancel remain separate from terminal input; Ctrl-C is not authoritative cancellation.

7. Results, capture requirements and feedback

Results is a first-class media feed: Latest, Needs review and Following. Scope, task, media type and time filters apply consistently. Latest sorts by submitted time and stable identity. New arrivals create a “New results available” prompt without moving the current card. Load bounded pages with a keyboard-accessible Load more option, thumbnails first, and no autoplay with sound. Pause offscreen video and retain a bounded window of cards while restoring reading position.

Each card contains a summary, task/project, originating attempt, exact result revision and source commit where applicable, submission time, required-evidence status, artifacts and separate acceptance status. A result may have no Git commit; it must declare the applicable source identity rather than inventing one. Open images at full resolution, clips with native accessible playback controls, and before/after comparisons with explicit artifact identities. Expired, processing, withheld, missing or failed media has an informative placeholder.

Capture requirements are a versioned task policy snapshot. Visual changes ordinarily request named desktop/mobile screenshots; interaction changes request a short clip demonstrating named steps; backend work requests tests, logs or API evidence. A backend task does not need a meaningless video. Server policy evaluates applicability and required evidence; the client displays its explanation.

Required artifacts must be finalized, retained and bound to the evaluated result revision before a configured completion gate passes. Presence alone does not prove correctness, acceptance or completion. A waiver requires the authorized actor, reason, requirement identity and policy revision. Editing requirements after an attempt starts is an explicit versioned change; it cannot silently make old evidence applicable to new criteria.

Comments may attach to a whole result revision, a normalized screenshot region or a video time/range. The UI shows exact pinned artifact/revision and the original annotation even if a later result supersedes it. Author and time are visible. Mobile uses a full-width comments sheet/page and an explicit media-expand action; touch placement is adjustable before posting.

Feedback flow:

  1. Post a comment. This creates discussion only; it does not reopen or schedule work.
  2. Choose Create feedback task, or Link existing task. A draft contains the requested change, acceptance criteria, project, parent task, result/artifact revision and annotation. The user can edit it.
  3. Submit with a stable operation ID and required version guards. Display pending/unknown/conflict faithfully; repeated clicks cannot create extra tasks.
  4. Follow the linked work. A later result references the original feedback and prior result.
  5. Show “Fix submitted” until the authorized reviewer or configured verification policy resolves the thread against an exact result revision. A successful task alone does not resolve the comment.

Capture only the intended application/test scenario. AQ enforces authorized upload/retrieval and media limits. Keep artifact references and tombstones when bytes expire so existing discussion still has intelligible provenance. The API proposal defines retention holds, bounds and partial-failure recovery.

8. Playbooks and Knowledge

Playbooks. Separate Runs, Definitions and Activations. A run shows its pinned artifact and transitive dependency versions, step timeline, current wait, child runs, pending operations, receipts and authorized actions. Updating an active definition does not relabel existing runs. Source editing, compilation, installation and activation are separate operations. Compilation validates structure; it is not proof of faithful policy translation. Human gates appear only where configured. Resuming a run cannot bypass the outstanding domain decision. Mobile uses a vertical step timeline and one detail page.

Knowledge. Search/filter by scope, category, lifecycle and verification independently. Detail shows document content, exact revision, author/provenance, sources, linked work, revision history, verification assertions and validity/review dates. Current and pinned history are unmistakable. A verifier's assertion is not proof of task completion. Retirement and successor links do not erase historical revisions. Authoring, correction, verification and retirement use separate permitted actions and expected versions; no generic JSON editor. Mobile opens one full document, with section navigation and metadata disclosures.

These breakpoints are initial design values; content fit and font scaling govern adaptations. Phone bottom destinations are Overview, Results, Supervisor, Agents and More. More includes Work, Decisions, Playbooks, Knowledge and Settings. Focused text entry may collapse bottom navigation; return restores it. At 320px, provider entries may wrap into two rows; never force whole-app horizontal scrolling. Essential two-dimensional content may scroll inside its own labelled region.

Target WCAG 2.2 AA, including keyboard operation, visible/unobscured focus, semantic headings/landmarks, labelled icons, contrast, status announcements and reduced motion. Use 44px primary touch targets as a product choice; WCAG's AA minimum target criterion is 24px with defined exceptions. Reflow exceptions for terminals/graphs do not exempt the rest of the application. See WCAG 2.2 and Reflow guidance.

Drawers/dialogs trap focus only while modal and restore it on close. Never announce every terminal frame through a live region. Provide a bounded transcript/read mode and explicit status changes. Clip instructions should have text equivalents; audio-bearing evidence needs captions/transcript when required for understanding. Color never carries a state alone. Static PNGs do not establish conformance.

10. Shared state and failure presentation

Every surface supports initial loading, successful empty, partial/truncated, stale, disconnected, unauthorized, unsupported and failed states. Keep previously fetched content only within the active identity/scope and mark its age. Unavailable data must not become a zero count. Server time/freshness drives age and expiry labels; local timers never authorize actions.

Permitted-action descriptors explain why an action is unavailable, but the server rechecks authorization on every request. Pending operations display their identity and reconciliation link. A lost response is unknown, not failure or success. Conflicts preserve the draft; changing the payload after conflict requires explicit resubmission with a new operation identity. Logout/identity change clears protected caches and drafts; display/layout preferences may persist without content.

Acceptance is defined by the scenario matrix in the implementation plan. The original U1–U14 remain required; this specification adds quota, responsive composition, expanded chat and the Results/feedback lifecycle.

Existing contracts are identified explicitly below. API-02 must publish versioned OpenAPI/JSON Schema, generated bindings, semantic validators and fixtures before dependent live integrations are accepted.

Related: product design, current contract audit, delivery plan. Browser traffic terminates at AQ's human listener. There is no new dashboard backend and no direct graph/worker/provider access.

2. Proposed public API conventions

New human resources use /api/v1/..., centrally registered in AQ's contract inventory. Paths in sections 3–7 are proposals unless listed as existing above. Common fields apply to new resources; owner adapters must explicitly map existing responses.

Type Required meaning
Id Opaque nonempty identifier, maximum 128 UTF-8 bytes; preserve existing UUID identities where applicable
Revision Positive decimal string; compare for equality, never infer ordering across resources
Timestamp UTC RFC3339 string with milliseconds; nullable only when explicitly unknown
Digest Algorithm-labelled SHA-256 digest of immutable bytes/canonical payload, with published canonicalization
Scope {kind:"all_authorized"} or {kind:"project", project_id:Id}; server derives the authorized set
EntityRef {type, id, revision?}; pins require revision, current pointers explicitly omit it
Observation {observed_at, fresh_until, source, quality:reported\|estimated\|unknown, coverage:complete\|partial\|unknown}
ActionDescriptor {kind, subject, allowed, reason_code?, explanation?, expected_versions, expires_at?}; UI hint, never a grant

All new reads return an envelope with api_version, request_id, server_time, scope, data, observation, pending_operations, and coverage:{state,omitted_count?,reason?}. Mutable entities carry their revision; immutable artifacts carry their digest. A composite read carries a revision vector/source watermarks, not a fictional cross-service transaction revision. Distinguish server-authoritative lifecycle fields from observations inside the response.

Collections use an opaque, authenticated cursor bound to principal, scope, normalized filters, sort and snapshot/watermark. Page size defaults to 25, maximum 100; Results defaults to 20. Stable order includes an ID tiebreaker. Return next_cursor, has_more, snapshot_id, and total:{value,accuracy:exact\|estimated\|unknown}. On expired cursors return a typed restart instruction; keep the user's reading anchor while refreshing. Newest items do not mutate an existing snapshot. Permission changes invalidate access immediately, including cached thumbnail/download retrieval.

IDs/cursors alone grant no access. Scope is checked for every returned entity, relationship endpoint, historical revision and artifact. All-authorized aggregation must not reveal excluded project counts. Validate bounded filters and reject unknown mutation fields. Server supplies maximum page/body/media limits through bootstrap and may lower defaults; clients obey lower limits.

The current human CSRF convention is X-AQ-Request: 1 on non-GET/HEAD requests, with same-origin validation when Origin is present. Use the configured human identity flow, never a worker or agent token. Scope/role changes invalidate protected query caches. No persistent sensitive offline cache is included.

3. Bootstrap and provider quota

Propose GET /api/v1/bootstrap:

type Bootstrap = {
  principal: { id: Id; display_name: string; authorization_revision: Revision };
  product: { version: string; dashboard_digest: Digest };
  contracts: { name: string; version: string; digest: Digest }[];
  capabilities: { name: string; version: string; enabled: boolean; reason?: string }[];
  limits: { page_size: number; media: MediaLimits; polling: PollingLimits };
  default_scope: Scope;
  global_supervisor: { status: "available" | "unconfigured" | "unavailable";
    conversation_id: Id | null; reason?: string };
};

Required capability families: dashboard.inspect, dashboard.actions, provider.quota, supervisor.conversation, terminal.watch, terminal.control, results.read, results.comment, results.feedback, artifacts.read, playbooks.inspect, knowledge.read. Independent mutations need their own permissions; a capability does not grant them. Exact capability spellings/version ranges are frozen in API-02 publication, not inferred from a server version number.

Propose GET /api/v1/provider-usage, account-scoped regardless of project filter:

type QuotaWindow = {
  id: Id; label: string; starts_at: Timestamp | null; resets_at: Timestamp | null;
  used_percent: number | null; used: number | null; limit: number | null;
  unit: string | null; state: "known" | "unknown" | "unavailable";
  observation: Observation;
};
type ProviderUsage = {
  provider_id: Id; account_ref: Id; account_label: string;
  scope: "provider_account"; windows: QuotaWindow[];
  preferred_window_id: Id | null; availability_ref: EntityRef | null;
};

used_percent is 0–100 when the upstream contract defines a capped ratio; any over-limit quantity is a separate explicit field in the published schema. Null means unknown. A reset may be unknown. No source percentage is inferred from token totals, worker slots or credential availability. The collector owns upstream semantics, authentication, freshness and shared-account deduplication; the browser never calls the provider. Adapter faults return stale/unknown observations, without blocking all other page content. API-02 must select and qualify actual quota sources; this audit found no provider quota reporting contract to reuse.

5. Supervisor conversation contract

Propose GET /api/v1/conversations/global, GET /api/v1/conversations/{id}/messages, and POST /api/v1/conversations/{id}/messages. The global route resolves a stable authorized conversation rather than guessing an active attempt. A new supervisor incarnation may participate in the same logical conversation but must retain exact delivery/authority identities.

Messages contain message_id, thread_id, conversation_id, server-derived author, created_at, UTF-8 text, pinned context refs, artifact refs and separate logical admission / node-or-host delivery / agent receipt fields. Maximum body initially 16,384 UTF-8 bytes, aligned with current mail; at most 16 context refs. Pagination supports reading older history and observing new messages without changing message identity. Attachments use the artifact service, not arbitrary URLs or base64 bodies in mail.

Sending carries operation_id, client-minted message_id, expected conversation revision and immutable body/context. The adapter must durably retain accepted intent before handing it to the existing mailbox mechanism. Specify how replies attach to conversation/thread and how oversized historical bodies are recovered. Global scope does not expose all projects: attached context and assistant replies remain authorized for the current reader.

AQ-17 is required for a central supervisor authority adapter. AQ-11 task/session mailbox identity does not by itself define global conversation identity. Reconnecting or switching dock/full presentation creates neither a message nor a session. Unknown delivery never causes automatic reinjection to a successor. A task proposal is a typed draft reference; executing it uses an authorized domain operation, not an interpretation of arbitrary message prose.

Human uploads use the human listener. Agent/worker capture producers need a separately authenticated machine ingestion adapter with frozen task/attempt/generation binding; they must never borrow a browser identity. Artifact storage and processing are AQ-owned services/modules even if bytes use configured object storage. AQ mediates access initially; a later signed-URL design needs explicit lifetime/revocation semantics.

Initial media policy: PNG/JPEG/WebP images up to 20 MiB and 40 megapixels; MP4/WebM clips up to 100 MiB and 120 seconds; UTF-8 text/log/JSON evidence up to 10 MiB. At most 20 artifacts and 250 MiB per result revision, subject to stricter server quotas. Use separate bounded upload admission; 4 MiB maximum parts, at most two concurrent parts per client. Validate actual file content and decoded dimensions/duration, not only declared MIME/extension. No active HTML/SVG execution. Serve inert metadata with content sniffing disabled. Text is escaped. Process thumbnails/transcodes asynchronously with resource ceilings and explicit failures. Original and derived digests are distinct. A processed variant does not silently replace the source.

Proposed retention default: unfinalized uploads expire after 24 hours; unheld retained result bytes expire 90 days after submission. Open review/feedback and accepted completion-evidence policy place explicit holds; holds cannot silently expire beneath an unresolved decision. Before release, publish per-project storage budgets and an authorized eviction/waiver process. Keep minimal scoped metadata/tombstones and annotation identities after byte deletion. Never claim retained evidence merely because metadata survives. Content retrieval rechecks permission; no public permanent media URLs.

Anchors are tagged unions:

type Anchor =
  | { kind: "result" }
  | { kind: "image_region"; artifact_id: Id; digest: Digest;
      x: number; y: number; width: number; height: number }
  | { kind: "video_range"; artifact_id: Id; digest: Digest;
      start_ms: number; end_ms: number };

Image coordinates use the displayed image after the server's documented orientation normalization, within [0,1], positive width/height and bounds ≤1. Video bounds are integer milliseconds, 0 ≤ start ≤ end ≤ duration; equal endpoints mean one instant. The artifact must belong to that result revision. Transformations may display anchors but cannot mutate their original meaning. Text comments are 1–16,384 UTF-8 bytes; initial nesting is one thread with ordered replies, not arbitrary recursive trees.

Feedback draft requires title (1–200 characters), description, acceptance criteria, authorized project/parent-task refs, origin thread/comment revision and result/artifact pins. AQ uses a durable intent/outbox with one fixed upstream graph key, then retains the created task receipt and feedback link. If task creation succeeds and linking is uncertain, operation status names the retained task when authorized and reconciles the link with the same identity. It must never repeat task creation under a new key. Thread resolution is a later independent guarded operation; linking and submitting a fix do not resolve it.

Following/Needs review are server-defined projections: Following is explicitly followed results plus the current user's opted-in feedback threads; Needs review means an unresolved applicable review/evidence decision, not merely an unread card. Changes to those definitions are versioned product semantics, not browser heuristics.

7. Actions, receipts and error contract

Propose POST /api/v1/actions for a finite tagged union of approved domain actions and GET /api/v1/operations/{id} for human lookup. Each action has its own published schema and adapter: task cancellation, typed decision response, authorized knowledge correction/verification/retirement, playbook start/cancel/activation and supported wait interventions. Do not expose arbitrary command names, URLs, shell fragments or graph mutations. Results-specific endpoints use the same durable operation semantics. Existing terminal operations keep their specialized contract.

New mutation envelope: {operation_id, kind, subject, expected_versions, reason?, payload}. Bind ID to principal, scope and canonical immutable request digest before dispatch. Identical retry returns the retained disposition; changed-byte reuse returns conflict. Authentication and current authorization are checked again on retry. An existing receipt cannot grant a new effect. Declare receipt retention in capability metadata; proposed ordinary action minimum is 90 days plus all unresolved operations, with retired-ID tombstones preventing replay after removal.

Disposition Browser behavior
pending Durable admission or in-flight work; show pending, poll original operation
confirmed Show exactly the confirmed effect and affected versions, then refresh relevant reads
conflict Show version/identity conflict; preserve draft; no automatic overwrite
rejected Definite refusal; show safe explanation and permitted next step
unknown Effect/admission may have occurred; retain original ID/bytes, query, never invent success or a new action

Operation response includes disposition, canonical request digest, created/updated times, subject refs, confirmed receipt refs, affected entities, and permitted recovery action. A missing lookup row means admission unknown unless the server can prove a stronger result. HTTP 202 is not completion. UI may show pending placeholders, never optimistic authoritative lifecycle changes.

New error envelope: {request_id,code,message,retryable,operation_id?,field_errors?,current_versions?,retry_after_ms?} with bounded safe strings. Use 401 for unauthenticated, 403 for unauthorized, neutral 404 for inaccessible/missing resources, 409 for conditional or identity conflicts, 410 for expired bytes/cursors where disclosure is authorized, 413 for limits, 422 for validation, 426 for unsupported required contract and 429/503 for bounded capacity/unavailability. Before durable admission an error may have no operation ID; after admission return the retained disposition where available. Transport failures alone never prove no effect. Unknown enum values render explicitly unsupported, disabling dependent actions rather than coercing to a success state.

8. Publication and contract acceptance

API-02 owns the human contract inventory and adapter behavior. Publish:

  1. Versioned OpenAPI/JSON Schema with explicit limits, enums and discriminators, plus generated TypeScript and a lossless integer strategy.
  2. Canonical fixtures for every successful, empty, partial, stale, unsupported, unauthorized, conflict, pending and unknown state; error and cursor fixtures included.
  3. Semantic tests for scoped projections, exact revisions, request digest/replay, expiry and receipt retention. Schema validity alone is insufficient.
  4. Compatibility manifest tying contract digests, server capabilities and bundle requirements. Unknown required capabilities block that feature; old tabs retain unsent drafts while presenting a safe upgrade path.
  5. Runtime integration evidence for the mounted human router, current identity/CSRF policy, actual domain adapters and the selected immutable product candidate.

The dashboard can build components against clearly labelled proposed fixtures now. A live integration is not complete until its published contract, mounted route, authorization, domain effect and recovery behavior are qualified together. Results storage, quota collection and central supervisor authority are explicit backend work, not frontend assumptions.

2. State, polling and failure behavior

Query keys include principal, authorization revision, project scope, filter, entity identity/revision and contract version. On identity change, abort requests and clear protected caches, drafts, media object URLs and terminal subscriptions. Persist only harmless preferences such as font size, density and panel layout. Drafts remain in memory across route/layout changes; unexpected page/process termination may lose them in the first release and must not be described as durable saving.

Do not automatically hard-reload an incompatible tab with unsent drafts. Keep a local read-only draft recovery view, allow copy/export under the current user, and ask the user to reload after preserving it. An expired authenticated session can hold an inaccessible in-memory draft pending reauthentication by the same principal; a different principal clears it.

Starting polling budget: foreground overview/active roster 10s, detail 5s, inactive history 30s, provider quota 60s subject to server freshness and limits. Pause hidden ordinary pages; refresh on focus with jitter and deduplication. Pending operations poll at 1s then exponential backoff to 15s, respect Retry-After, and remain pending/unknown after a bounded foreground wait. Only one request per query key in flight. A client-wide scheduler caps ordinary domain requests at four concurrent and staggers refreshes. These are initial measurement targets, not accepted server capacity.

Terminal output follows its negotiated bounded transport independently. Do not invent a WebSocket requirement: the current adapter exposes bounded HTTP output reads and specialized mutations. Rendering occurs outside React message-by-message state; batch frames within the transport limits, signal gaps and request legitimate resynchronization. Watch acquisition and controller acquisition use distinct state machines. Terminal input never uses a generic optimistic mutation/retry helper.

Ordinary mutations allocate one operation ID when a draft is submitted, freeze bytes until a known disposition, and expose lookup/reconciliation. A click handler cannot allocate multiple actions while the first is unresolved. Only a deliberate changed submission creates a new ID. Persisted server operation discovery must allow recovery after a tab reload without persisting sensitive request bodies locally. Telemetry records route, capability, latency and opaque correlation IDs, never terminal text, chat bodies, raw input or media contents.
